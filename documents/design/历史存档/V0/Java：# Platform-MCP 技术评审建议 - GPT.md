## 1. 总体评审结论

从两份文档描述看，Platform_MCP 采用 **Java 单体模块化架构 + MCP 统一入口 + Database Skill 首期落地 + Web 管理端 + PostgreSQL 系统库 + JDBC 目标库访问** 的总体路线，符合一期内部平台建设的可控性要求。

整体方案具备以下特点：

1. **一期可落地性较强**  
   首期聚焦 database skill，不引入微服务、Docker/K8s、复杂审批流、大规模调度等高复杂度能力，符合“小范围先落地、稳定后扩展”的实施原则。

2. **软件兼容性风险可控但需要前置验证**  
   文档已经识别 Oracle 11g、MySQL 5.6、JDK、Spring Boot、JDBC 驱动之间的兼容性风险，并给出 Spring Boot 3.2.8 / JDK 17 的目标方案及 Spring Boot 2.7.18 / JDK 11 的回退策略。该方向合理，但必须在正式开发前完成专项联调验证。

3. **二期扩展基础已经预留**  
   MCP 层通过 skill-api、skill-registry、mcp-core 等模块抽象出统一入口和注册机制，为后续 file、log、config、deploy 等 Skill 扩展预留了基础能力。

4. **首期范围仍需进一步收敛**  
   当前文档中首期页面、模块、审计、安全、状态监控、风险识别等内容较完整，但对一期来说范围偏满。建议首期明确最小可交付版本，优先保证 MCP 调用、数据库执行、权限控制、数据源管理、审计闭环可用。

## 2. 一期可行性评审

### 2.1 架构路线可行

文档建议采用 Java 单体模块化架构，后端内部按 web-admin、auth、datasource、crypto、mcp-core、skill-api、skill-registry、skill-database、sql-executor、risk-engine、audit、monitor 等模块划分。

该方案对一期是可行的，原因如下：

- 单体部署降低了首期部署、运维、排障复杂度；
- 模块化设计可以在代码层面保持边界清晰；
- Java + Spring Boot 更适合企业内部权限、审计、配置、后台管理类系统；
- JDBC 对 Oracle 11g、MySQL 5.6 等老数据库接入更成熟；
- Jar + systemd + Nginx 的部署方式与传统内部系统运维模式匹配。

### 2.2 一期范围建议进一步分级

文档中首期纳入范围包括：

- Java 后端服务建设；
- Web 管理端建设；
- MCP 统一入口建设；
- Database Skill 实现；
- 用户/角色/权限管理；
- 数据源管理；
- 密码加解密管理；
- 审计日志；
- MCP 调用状态页；
- PostgreSQL 系统库建设；
- Oracle 11g / MySQL 5.6 兼容接入。

这些内容整体合理，但如果全部作为一期一次性交付，实施压力较大。建议一期内部再拆成“必须交付”和“增强交付”。

#### 一期必须交付能力

建议优先保证以下能力：

1. **MCP 基础入口**
   - 接收 Claude Code 调用；
   - 支持 Tool 参数解析；
   - 支持统一响应结构；
   - 支持 traceId / requestId。

2. **Database Skill 最小闭环**
   - `execute_sql_file`；
   - `execute_sql_text`；
   - `list_datasources`；
   - 基础执行结果返回。

3. **数据源管理**
   - 数据源新增、修改、启停；
   - 数据库类型、环境、JDBC URL、驱动类、密文密码配置；
   - 数据源权限控制。

4. **权限与认证**
   - 管理端登录；
   - 用户、角色、权限基础模型；
   - MCP Tool、环境、数据源维度的访问控制。

5. **密码加密能力**
   - 明文密码加密；
   - 密文存储；
   - secret 文件独立存储；
   - 解密操作仅限授权管理员。

6. **审计闭环**
   - MCP 调用日志；
   - SQL 执行日志；
   - 数据源配置变更日志；
   - 密码加解密操作日志；
   - 权限变更日志。

7. **Oracle / MySQL 基础兼容验证**
   - Oracle 11g 连接；
   - MySQL 5.6 连接；
   - SELECT / INSERT / UPDATE / DELETE 基础执行；
   - 事务提交与回滚。

#### 一期可后置增强能力

以下能力建议作为一期后半段或二期前置增强，不建议阻塞最小可用版本上线：

- ECharts 监控图表；
- 复杂 MCP 状态统计；
- 完整 SQL 风险识别规则；
- Oracle PL/SQL 块复杂拆分；
- 多语句执行的完整跨库兼容；
- 存储过程高级调用与游标结果处理；
- SonarQube 等质量平台集成；
- 压力测试体系深度建设。

### 2.3 一期最大实施风险

#### 风险一：SQL 文件多语句拆分复杂度偏高

文档已指出按分号拆分需要处理注释、字符串常量、PL/SQL 块等特殊情况。该点是一期开工后最容易超出预期的复杂点。

建议：

- 一期不要承诺完全通用 SQL 脚本解析能力；
- 对 Oracle PL/SQL 块、存储过程、触发器类脚本先定义能力边界；
- 对简单 DML / DDL / SELECT 脚本优先支持；
- 对复杂脚本可以要求单语句执行或采用明确分隔符规范；
- 风险识别解析失败时应返回明确提示并写入审计。

#### 风险二：Web 管理端范围偏宽

首期页面包含登录、首页、数据源管理、密码加解密、用户管理、角色权限、审计日志、MCP 状态、系统配置等，页面数量较多。

建议：

- 一期优先完成登录、数据源管理、密码加解密、审计日志、MCP 调用状态页；
- 用户/角色权限管理可先实现基础配置能力；
- 系统配置页可只保留必要参数，不做复杂配置中心；
- 首页概览可先做简版统计，不作为关键路径。

#### 风险三：权限模型维度较多

文档建议权限覆盖用户、角色、Skill、Tool、环境、数据源、页面功能点。该模型是正确方向，但一期全部精细化实现会增加设计和测试成本。

建议：

- 一期权限模型保留完整数据结构；
- 首期执行控制重点落在 Tool + 环境 + 数据源；
- 页面功能点权限可先做到菜单级或按钮级基础控制；
- 后续再扩展到更细粒度策略。

## 3. 软件兼容性评审

### 3.1 JDK 与 Spring Boot 兼容性

文档建议正式目标版本为：

- JDK 17.0.12 LTS；
- Spring Boot 3.2.8；
- Spring Framework 6.1.12；
- Spring Security 6.2.5。

同时保留回退策略：

- Spring Boot 2.7.18；
- Spring Security 5.8.x；
- JDK 17 或 JDK 11。

该设计是合理的，但建议将兼容性决策前置为启动准入条件。

建议在正式开发前完成以下验证：

1. JDK 17 + Spring Boot 3.2.8 + PostgreSQL 16.4；
2. JDK 17 + Spring Boot 3.2.8 + Oracle 11g + ojdbc8 19.22.0.0；
3. JDK 17 + Spring Boot 3.2.8 + MySQL 5.6 + mysql-connector-java 5.1.49；
4. 如 Oracle 验证失败，再验证 JDK 11 或 Spring Boot 2.7.18 回退组合。

建议形成明确结论：

- 首选组合是否可用；
- Oracle 驱动最终版本；
- MySQL 驱动最终版本；
- 是否启用 Spring Boot 2.7.18 回退方案；
- 生产环境 JDK 最终版本。

### 3.2 Oracle 11g 兼容性

文档已识别 Oracle 11g 的主要关注点：

- JDBC 驱动兼容性；
- 字符集；
- 日期时间类型；
- 存储过程调用方式；
- 游标处理；
- 多语句与 PL/SQL 块解析。

建议一期将 Oracle 支持拆成基础支持与增强支持。

#### Oracle 一期基础支持

- 建立连接；
- 执行 SELECT；
- 执行 INSERT / UPDATE / DELETE；
- 执行简单 DDL；
- 支持事务提交和回滚；
- 支持基础错误信息返回；
- 写入完整审计。

#### Oracle 后续增强支持

- 存储过程 OUT 参数；
- REF CURSOR；
- PL/SQL 块批量执行；
- 复杂脚本解析；
- 多结果集处理。

### 3.3 MySQL 5.6 兼容性

文档建议使用 mysql-connector-java 5.1.49，该建议合理。MySQL 5.6 是老版本，使用 8.x 驱动可能引入旧认证、时区、字符编码等兼容问题。

建议重点验证：

- 连接参数中的字符集配置；
- 时区参数；
- 多语句执行开关；
- 事务隔离与提交行为；
- DDL / DML 返回影响行数；
- 大字段和日期字段读取。

### 3.4 PostgreSQL 系统库兼容性

文档建议 PostgreSQL 16.4 作为系统库。该选型适合管理类数据、日志、配置和权限关系存储。

建议注意：

- 系统库版本较新，与目标库版本较老无直接冲突；
- 系统库访问应与目标库访问严格隔离；
- 系统库可使用 MyBatis 管理，目标库建议保持原生 JDBC 或轻量封装；
- 审计日志和调用日志需考虑数据量增长后的索引与归档策略。

### 3.5 前端技术兼容性

文档建议：

- Node.js 20.15.1 LTS；
- Vue 3.4.38；
- Vite 5.4.2；
- TypeScript 5.5.4；
- Element Plus 2.8.1。

该组合较成熟，适合后台管理端。

建议：

- 锁定 Node.js 主版本和 npm 版本；
- 使用 lock 文件固化依赖；
- 避免频繁升级 Element Plus 小版本；
- 前端只承担展示、表单校验和接口调用，不实现真实权限判定、SQL 执行和密码加解密。

### 3.6 部署兼容性

文档建议 Jar + systemd + Nginx，不使用 Docker/K8s。该方案符合一期简单稳定原则。

建议补充关注：

- Linux 发行版与 JDK 安装方式统一；
- systemd 启停、重启、日志路径标准化；
- secret 文件权限收敛；
- 应用配置、日志目录、脚本目录分离；
- Nginx 访问日志与应用 traceId 的关联方式。

## 4. 二期扩展性评审

### 4.1 MCP Skill 扩展方向合理

两份文档均明确：MCP 层不应固化为仅 SQL 执行模块，而应作为统一能力入口。首期落地 database skill，后续预留 file、log、config、deploy、shell 等 Skill。

该扩展方向合理，但二期能否顺利扩展，取决于一期是否真正固化以下机制：

- Skill 统一接口；
- Tool 元数据定义；
- Skill 注册机制；
- Tool 到 Skill 的路由机制；
- 权限模型对 Skill / Tool 的抽象；
- 审计日志对不同 Skill 的统一记录；
- MCP 状态页按 skill/tool 维度展示。

### 4.2 一期必须避免 database skill 侵入核心层

二期扩展最大的风险是首期 database skill 逻辑反向侵入 mcp-core、skill-registry、audit、monitor 等公共模块，导致后续新增 Skill 时需要改动核心框架。

建议：

- `mcp-core` 只处理协议接入、参数标准化、上下文、响应封装；
- `skill-api` 只定义统一接口和输入输出模型；
- `skill-registry` 只负责注册、发现和路由；
- database 相关 SQL、数据源、风险识别逻辑不得写入 mcp-core；
- audit 和 monitor 需按 skill/tool 维度设计，而不是按 SQL 专用字段设计。

### 4.3 Skill 接口建议首期稳定

文档建议每个 Skill 实现具备：

- skillName();
- listTools();
- validate();
- execute();
- support();

该设计可作为二期扩展基础。建议一期即明确：

- Tool 名称规范；
- Tool 输入参数描述；
- Tool 输出结构；
- 参数校验失败返回格式；
- 执行异常返回格式；
- 权限拒绝返回格式；
- 审计字段要求。

### 4.4 权限与审计结构需面向通用 Skill

如果一期权限和审计仅围绕数据库字段设计，二期扩展 file、log、config 等 Skill 时会遇到结构不匹配问题。

建议审计主表保留通用字段：

- trace_id；
- request_id；
- operator；
- skill_name；
- tool_name；
- request_summary；
- result_status；
- risk_level；
- error_message；
- start_time；
- end_time；
- duration_ms。

数据库专有字段如 datasource_code、env_code 可作为可选字段或扩展字段，不应成为所有 Skill 的强制字段。

### 4.5 二期扩展不建议过早引入微服务

文档首期明确不采用微服务拆分，这是合理的。二期即使扩展多个 Skill，也不一定需要立即微服务化。

建议二期演进顺序为：

1. 先扩展 Skill 类型；
2. 再完善注册、权限、审计、状态监控；
3. 当不同 Skill 的依赖、发布节奏、资源消耗明显分化后，再评估是否拆分服务；
4. 不建议仅因 Skill 数量增加就提前微服务化。

## 7. 建议的一期验收标准

一期验收建议聚焦可用闭环，而不是能力铺满。

### 7.1 功能验收

- Claude Code 可通过 MCP 调用 database skill；
- 可执行 SQL 文本；
- 可执行受控范围内的本地 `.sql` 文件；
- 可查询可用数据源；
- 可查看 MCP 调用状态；
- 可查看审计日志；
- 可配置数据源及密文密码；
- 可按用户/角色/数据源/环境控制访问。

### 7.2 兼容性验收

- Oracle 11g 基础连接和 SQL 执行通过；
- MySQL 5.6 基础连接和 SQL 执行通过；
- PostgreSQL 系统库访问稳定；
- 目标数据库连接失败时不影响系统库和管理端；
- 驱动版本、JDK 版本、Spring Boot 版本形成最终固化清单。

### 7.3 安全与审计验收

- 目标数据库密码不明文入库；
- secret 文件不写入代码；
- 解密操作受权限控制；
- SQL 执行全链路可追踪；
- MCP 调用、配置变更、权限变更均有审计记录。

### 7.4 运维验收

- 支持 Jar 启动；
- 支持 systemd 启停；
- 支持 Nginx 反向代理；
- 日志按目录输出；
- 配置文件与 secret 文件分离；
- 服务异常可通过日志定位。

## 8. 二期扩展建议

二期建议围绕“在不推翻一期框架的前提下扩展 Skill 能力”展开。

### 8.1 Skill 类型扩展

可按优先级逐步扩展：

1. `log skill`：日志查询、错误定位、调用链检索；
2. `file skill`：受控文件读取、配置查看；
3. `config skill`：系统参数查询与受控调整；
4. `deploy skill`：部署状态查看、版本信息查询；
5. `shell skill`：如需支持，应放在严格权限和审计之后评估。

### 8.2 平台能力增强

- Tool 元数据管理；
- Skill 启停控制；
- Skill 权限模板；
- MCP 调用趋势统计；
- 审计日志归档；
- 风险规则可配置；
- 更细粒度的数据源权限策略。

### 8.3 数据库能力增强

- Oracle 存储过程高级支持；
- MySQL 多语句执行增强；
- SQL 解析能力增强；
- SQL 执行计划辅助查看；
- 高危 SQL 二次确认或审批机制；
- 审计日志与执行结果更细粒度关联。

## 9. 最终评审意见

### 9.1 一期可行性意见

一期方案总体可行，建议批准按 Java 单体模块化路线推进。但一期范围应以 MCP + database skill + 数据源管理 + 权限 + 审计 + 基础 Web 管理闭环为核心，不建议在首期追求完整 SQL 平台化能力、复杂脚本解析能力和完整监控分析能力。

### 9.2 软件兼容性意见

软件兼容性是本项目一期最关键的前置风险。建议将 Oracle 11g、MySQL 5.6、JDK、Spring Boot、JDBC 驱动组合验证作为正式开发前的准入项。若 Oracle 11g 在 JDK 17 + Spring Boot 3.2.8 下存在不可接受风险，应及时切换到文档中预留的 Spring Boot 2.7.18 / JDK 11 回退方案。

### 9.3 二期扩展性意见

二期扩展基础设计合理，但前提是一期必须真正固化 mcp-core、skill-api、skill-registry、audit、monitor 的通用边界，避免 database skill 逻辑污染核心框架。建议二期优先扩展 log、file、config 等低风险 Skill，再评估 deploy、shell 等高风险能力。

### 9.4 综合结论

建议项目按当前 Java 技术路线继续推进，评审结论为：

- **一期建设方向可行**；
- **软件兼容性需前置验证后固化版本组合**；
- **首期范围需适度收敛，优先保证最小可用闭环**；
- **二期扩展能力具备基础，但依赖一期 Skill 接口和注册机制的严格落地**。
