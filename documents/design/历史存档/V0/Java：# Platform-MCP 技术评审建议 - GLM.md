# 2. 一期功能实现评审

## 2.1 模块粒度 — 13 模块偏细，建议一期精简

### 现状
技术架构文档规划了 13 个模块：`web-admin`、`auth`、`datasource`、`crypto`、`mcp-core`、`skill-api`、`skill-registry`、`skill-database`、`sql-executor`、`risk-engine`、`audit`、`monitor`、`common`。

### 评审意见
一期仅落地一个 Skill（database），13 个模块对首期而言拆分过细，带来以下风险：

- **开发效率降低**：模块间接口定义、联调成本在首期占比过高
- **过度抽象**：`skill-api`、`skill-registry` 在只有一个 Skill 时，接口设计缺乏真实场景校验
- **职责模糊边界**：`monitor` 与 `audit` 职责有重叠（MCP 调用状态 vs MCP 调用日志）

### 建议

**一期建议合并为 7-8 个模块：**

| 合并后模块 | 包含原模块 | 说明 |
|---|---|---|
| `Platform-MCP-web-admin` | web-admin | Web 管理接口，不变 |
| `Platform-MCP-auth` | auth | 认证鉴权，不变 |
| `Platform-MCP-datasource` | datasource + crypto | 数据源管理与密码加解密天然耦合，合并减少模块间调用 |
| `Platform-MCP-mcp-core` | mcp-core + skill-api + skill-registry | 一期 Skill 注册逻辑极简，三层合一降低复杂度 |
| `Platform-MCP-skill-database` | skill-database + sql-executor + risk-engine | 数据库 Skill 内聚，执行器和风控引擎是其内部组件 |
| `Platform-MCP-audit` | audit + monitor | 审计日志与状态统计统一管理 |
| `Platform-MCP-common` | common | 通用工具，不变 |

**二期扩展时再拆分**：当第二个 Skill 落地时，从 `mcp-core` 中提取 `skill-api` 和 `skill-registry`，此时有真实场景校验接口设计。

## 2.2 实施优先级 — 审计应贯穿，非独立阶段

### 现状
技术架构文档将实施分为三阶段：

- 第一阶段：框架 + 认证 + 数据源 + 加密 + 系统库
- 第二阶段：MCP Core + Database Skill + SQL 执行器 + 审计日志
- 第三阶段：状态页 + 风险增强 + 兼容联调 + 运维

### 评审意见
审计被放在第二阶段，意味着第一阶段的认证、数据源管理、加密操作在开发期间**没有审计能力支撑**。这与两份文档均强调的"审计优先"原则矛盾。

### 建议

**审计应作为横切关注点，从第一阶段开始同步建设：**

| 阶段 | 内容 | 审计覆盖 |
|---|---|---|
| **第一阶段** | 框架 + 认证 + 数据源 + 加密 + 系统库 + **审计基础设施** | 登录日志、数据源变更、加密操作 |
| **第二阶段** | MCP Core + Database Skill + SQL 执行器 + 风控 | MCP 调用日志、SQL 执行日志、风险记录 |
| **第三阶段** | 状态页 + 兼容联调 + 运维 | 调用量统计、运行状态 |

审计模块在一期只需提供：
- 统一的 `AuditLogger` 接口
- `sys_audit_log` 表写入能力
- 各模块通过接口调用写入审计记录

不需要完整的审计查询页面（可放第三阶段），但写入能力必须提前。

## 2.3 MCP 协议落地方式 — 需明确 SDK 选型与进程模型

### 现状
两份文档均提到"MCP Server 接入"和"MCP Tool 接口"，但未明确：
- 使用官方 MCP Java SDK 还是自己实现协议
- MCP Server 的进程模型（stdio / HTTP SSE）

### 评审意见
MCP 协议是本项目的核心接入方式，选型不当会直接影响 Claude Code 调用链路。

**关键风险：**
- MCP 官方 SDK（TypeScript/Python）成熟度高，Java SDK 生态相对薄弱
- stdio 模式下，MCP Server 作为子进程由 Claude Code 启动管理；HTTP SSE 模式下，MCP Server 作为独立服务运行
- Claude Code 当前支持的 MCP Server 接入方式需要确认

### 建议

1. **确认 Claude Code 的 MCP 接入方式**：优先确认 Claude Code 期望的 MCP Server 运行模式（stdio / SSE）
2. **优先采用 MCP 官方 Java SDK**（如已发布正式版），避免自研协议实现带来维护负担
3. **若 Java SDK 不成熟，考虑以下备选方案：**
   - 方案 A：后端服务同时暴露 HTTP SSE 的 MCP 接口 + Web REST API，Claude Code 通过 SSE 连接
   - 方案 B：轻量 Node.js/Python 网关层接收 Claude Code 的 MCP 调用，转发至 Java 后端 REST API
4. **项目启动前完成 MCP 协议 PoC**：用一个最简 Tool（如 `list_datasources`）跑通 Claude Code → MCP Server → 后端 → 数据库全链路

## 2.4 SQL 文件执行安全 — 路径校验缺失

### 现状
`execute_sql_file` Tool 接收文件路径，读取本地 `.sql` 文件执行。文档未提及路径安全约束。

### 评审意见
接受外部传入的文件路径读取本地文件，存在以下安全风险：

- **路径穿越**：传入 `../../etc/passwd` 或类似路径读取非预期文件
- **符号链接攻击**：通过符号链接指向敏感文件
- **任意文件读取**：MCP 调用方可能利用此能力读取服务器任意文件

### 建议

1. **配置允许读取的根目录白名单**（如 `/opt/Platform-MCP/sql-scripts/`）
2. **校验解析后的绝对路径是否在白名单目录内**
3. **禁止符号链接跟随**（或解析后校验真实路径）
4. **限制文件扩展名**：仅允许 `.sql`
5. **限制文件大小**：防止读取超大文件导致内存溢出

```
// 伪代码示例
String baseDir = "/opt/Platform-MCP/sql-scripts/";
Path resolved = basePath.resolve(userPath).normalize().toAbsolutePath();
if (!resolved.startsWith(baseDir)) {
    throw new SecurityException("路径超出允许范围");
}
```

## 2.5 风险引擎范围控制 — 一期不应过度投入

### 现状
风险引擎规划了：语句类型识别、DDL/DML 判断、WHERE 缺失检测、全表操作检测、DROP/TRUNCATE 高危标记、解析失败记录。

### 评审意见
对一期而言，风险引擎的功能范围合理，但实现深度需要控制：

- **AST 级别的 SQL 解析**（如使用 JSqlParser）对 Oracle PL/SQL、存储过程支持有限
- **正则 + 关键词匹配**对常见场景够用，但需要承认其局限性
- **风险等级判定**（LOW/MEDIUM/HIGH/CRITICAL）的阈值需要与业务方对齐

### 建议

1. **一期采用正则 + 关键词匹配**，不引入 SQL AST 解析器
2. **明确标注风险引擎的局限性**：告知调用方风险识别为"辅助参考"，不保证 100% 准确
3. **对 DROP、TRUNCATE、DELETE WITHOUT WHERE 等高危操作默认阻断**，需要明确的确认机制
4. **解析失败的 SQL 统一标记为 HIGH 风险**，保守处理
5. **风险规则可配置化**：通过 `sys_system_config` 表管理规则开关，无需改代码即可调整

# 3. 版本兼容评审

## 3.1 Spring Boot 双版本策略 — 建议启动前锁定一条路线

### 现状
技术架构文档提供了优先/回退双策略：

- 优先：Spring Boot 3.2.8 + JDK 17
- 回退：Spring Boot 2.7.18 + JDK 17/11

### 评审意见
双版本策略虽然在文档层面是"建议"，但在实际开发中会导致：

- **依赖管理复杂度翻倍**：两套 Spring Security、MyBatis Starter、Actuator 等依赖版本需分别验证
- **代码兼容性维护**：`javax.*` vs `jakarta.*` 包名差异（Spring Boot 3.x 切换到 Jakarta EE 命名空间）
- **测试矩阵膨胀**：Oracle 驱动 × Spring Boot 版本 × JDK 版本的组合测试

### 建议

1. **在项目启动前 2 周内完成 PoC 验证**：
   - 验证场景：JDK 17 + Spring Boot 3.2.8 + ojdbc8 19.22.0.0 → 连接 Oracle 11g
   - 验证场景：JDK 17 + Spring Boot 3.2.8 + mysql-connector-java 5.1.49 → 连接 MySQL 5.6
   - 验证通过则锁定 3.2.8 路线，**删除回退策略**
2. **若 PoC 验证失败，直接锁定 2.7.18 路线**，不保留"后续可能升级"的模糊空间
3. **无论选择哪条路线，统一使用 JDK 17**，JDK 11 不到万不得已不降级

## 3.2 Oracle 11g 驱动兼容 — 需专项验证

### 现状
推荐 `ojdbc8 19.22.0.0`，备选 `ojdbc6 11.2.0.4`。

### 评审意见
Oracle 11g + JDK 17 + ojdbc8 19.x 的组合存在以下已知关注点：

- **ojdbc8 19.x 官方认证支持 Oracle 19c/21c**，对 Oracle 11g 的支持为"尽力兼容"而非"官方认证"
- **ojdbc6 11.2.0.4 不支持 JDK 17**（仅支持 JDK 6/8），降级到 ojdbc6 意味着同时降级 JDK
- **Oracle 11g 已于 2020 年结束扩展支持**，驱动层面的兼容性会越来越难保障

### 建议

1. **PoC 验证清单：**

   | 验证项 | 验证内容 |
   |---|---|
   | 连接建立 | Basic/TNS 连接方式 |
   | 字符集 | AL32UTF8 / ZHS16GBK 场景 |
   | 日期类型 | DATE / TIMESTAMP 读写 |
   | 存储过程 | IN/OUT/INOUT 参数、REF CURSOR |
   | CLOB/BLOB | 大字段读写 |
   | 事务控制 | autocommit=false + commit/rollback |

2. **若 ojdbc8 + JDK 17 连接 Oracle 11g 存在问题**，评估以下选项：
   - 选项 A：降级 JDK 到 11 + 使用 ojdbc8 12.x 版本
   - 选项 B：升级 Oracle 到 19c（如果运维条件允许）
3. **在 `sql-executor` 模块中设计数据库类型适配层**，将 Oracle 特有逻辑（如分页、存储过程调用）隔离在策略类中

## 3.3 MySQL 5.6 驱动 — 正确但需关注长期维护

# 4. 二期扩展评审

## 4.1 Skill 插件机制 — 缺少动态注册与热加载设计

### 现状
Skill 通过 `skill-api` 定义接口、`skill-registry` 负责注册。文档描述的扩展方式为"新增 Skill 模块 + 注册到 Registry"。

### 评审意见
当前设计隐含的是**编译期静态注册**：新增 Skill 需要修改代码、重新打包、重启服务。这对内部系统是可接受的，但缺乏以下能力：

- **运行时动态发现**：无法在不重启的情况下上线新 Skill
- **Skill 版本管理**：无法灰度发布或回滚某个 Skill
- **Skill 隔离**：一个 Skill 的异常不影响其他 Skill

### 建议

1. **一期采用编译期静态注册即可**，满足首期一个 Skill 的场景
2. **二期扩展时增强 Registry：**
   - 支持 Spring Bean 自动扫描注册（`@Skill` 注解 + `SkillRegistry` 自动收集）
   - 支持通过数据库配置控制 Skill 启用/禁用
   - 每个 Skill 独立 ClassLoader 隔离（可选，视复杂度而定）
3. **Skill 接口在一期即固化**，但要预留 `initialize()` 和 `destroy()` 生命周期方法

---

## 4.2 目标数据库连接池生命周期管理

### 现状
技术架构文档明确提出"根据执行请求按需建立连接，不长期持有连接池"。

### 评审意见
按需连接策略对一期合理，避免长期持有大量老库连接。但需要补充：

- **连接超时控制**：目标数据库连接建立超时、SQL 执行超时的默认值与可配置性
- **连接泄漏检测**：按需建立的连接如果异常未关闭，需要有兜底回收机制
- **并发连接控制**：对同一目标数据库的同时连接数上限
- **连接失败重试策略**：目标库短暂不可用时的处理方式

### 建议

1. **一期在 `sql-executor` 中实现：**
   - 每次执行创建连接 → 执行 → 关闭（try-with-resources）
   - 全局配置 `connection.timeout`（默认 30s）和 `query.timeout`（默认 300s）
   - 对每个数据源维护一个 `Semaphore` 控制最大并发连接数（默认 5）
2. **二期考虑引入轻量连接池（如每数据源独立 HikariCP 实例）：**
   - 适用于高频调用的数据源
   - 池化参数按数据源独立配置
   - 空闲超时自动回收

## 4.3 流式响应 — 长时间 SQL 执行的超时风险

### 现状
两份文档均未提及长时间 SQL 执行的响应策略。

### 评审意见
部分 SQL 执行（如大表 DDL、批量数据处理）可能耗时数分钟甚至更久。MCP 协议层面如果同步等待完整结果：

- **Claude Code 侧可能超时断开**
- **用户无法感知执行进度**
- **服务器资源长时间被占用**

### 建议

1. **一期实现：**
   - SQL 执行设置超时上限（默认 5 分钟），超时自动终止
   - 超时后返回"执行超时"状态，调用方通过 `get_execution_status` 查询最终结果
   - 异步执行模式：`execute_sql_file/text` 立即返回 `executionId`，结果通过 `get_execution_status` 获取
2. **二期评估：**
   - MCP SSE 流式返回执行进度（如果 MCP 协议支持）
   - Web 端实时展示执行进度（WebSocket）

---

## 4.4 限流与熔断 — 防止 MCP 调用压垮生产库

### 现状
两份文档均未提及限流和熔断机制。

### 评审意见
MCP 调用方（Claude Code）的调用频率和并发度不受本系统控制。在以下场景存在风险：

- Claude Code 并发发起多个 SQL 执行请求
- 循环调用 `execute_sql_text` 执行批量操作
- 对同一生产库的并发查询导致锁竞争或性能下降

### 建议

1. **一期在 MCP Core 层实现基础限流：**
   - 全局 MCP 调用并发上限（如同时 10 个）
   - 按数据源的并发上限（如每库同时 3 个）
   - 按调用方的速率限制（如每分钟最多 30 次调用）
2. **限流策略存储在 `sys_system_config` 表中，支持动态调整**
3. **二期考虑集成 Resilience4j：**
   - 按数据源的熔断器（连续失败 N 次后自动熔断）
   - 按数据源的慢调用比率熔断
   - 熔断后返回明确的"数据源暂时不可用"状态

---

## 4.5 多环境隔离策略

### 现状
通过 `env_code`（如 DEV/TEST/PROD）标识数据源环境。权限控制按 Skill + Tool + 数据源 + 环境维度。

### 评审意见
逻辑隔离（env_code）对一期够用，但存在以下风险：

- **误操作生产库**：env_code 仅是标签，不阻止代码层面的错误
- **配置错误**：开发环境数据源配置指向生产库的 IP，权限校验仍通过
- **缺少操作水位分离**：高危操作（DROP/TRUNCATE）在测试环境可执行，在生产环境需额外审批

### 建议

1. **一期：**
   - 生产库（`env_code=PROD`）的数据源默认标记为"受保护"
   - 受保护数据源的所有 DDL 和 DELETE WITHOUT WHERE 操作强制标记为 CRITICAL 风险
   - 通过配置控制受保护数据源的写入操作是否需要额外确认
2. **二期：**
   - 引入"操作审批流"：生产库高危操作需 Web 端二次确认
   - IP 白名单校验：数据源配置中绑定允许连接的来源 IP 段
   - 操作窗口控制：限制高危操作只能在指定时间段执行

---

## 4.6 Skill 间协作与编排

### 现状
两份文档未提及 Skill 间是否允许互相调用或编排。

### 评审意见
随着 Skill 数量增长（file、log、config 等），可能出现跨 Skill 的编排需求：

- "查询数据库 + 导出结果到文件" → database skill + file skill
- "读取配置 + 执行 SQL" → config skill + database skill

如果一期不定义 Skill 间协作规范，二期可能出现紧耦合的实现。

### 建议

1. **一期不实现 Skill 间调用**，但在 `skill-api` 接口设计中预留 `context` 参数
2. **二期评估是否引入 Pipeline/Workflow 概念：**
   - 调用方可指定一组有序的 Skill+Tool 组合
   - 前一个 Tool 的输出作为后一个 Tool 的输入
   - 编排逻辑由 MCP Core 统一调度，各 Skill 互不直接依赖

# 6. 总结

Platform_MCP 的核心架构方向（Java 单体模块化 + MCP 统一入口 + Skill 插件式扩展）是合理的。两份架构文档在系统定位、模块职责、技术选型、安全设计等方面覆盖全面。

本次评审识别的主要改进方向：

1. **模块粒度**：一期 13 模块过细，建议精简到 7-8 个
2. **审计贯穿**：审计写入能力应从第一阶段开始建设
3. **MCP 落地**：启动前必须确认 Claude Code 的 MCP 接入方式并完成 PoC
4. **版本锁定**：启动前通过 PoC 锁定 Spring Boot 单一路线
5. **安全加固**：SQL 文件路径校验、生产库保护、并发限流
6. **二期预留**：Skill 接口固化、连接池生命周期、流式响应、环境隔离增强

以上建议不改变项目整体方向，旨在降低一期落地的工程风险，为二期扩展奠定更扎实的技术基础。
