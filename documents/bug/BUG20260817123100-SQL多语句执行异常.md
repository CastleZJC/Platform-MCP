# BUG：SQL 多语句执行异常（DDL 执行失效）— 多语句不支持、confirm_token 回路无指引、`/` 碎片、业务失败未入审计

**严重级别**：Critical（DDL 核心链路失效）+ High（审计正确性缺陷）
**发现日期**：2026-08-17 12:31
**发现方式**：内部用户反馈"DDL 失效，仅可用 DML" → 本地实证定位（风险分级 + sqlparse 分句 + 审计行为三层验证）
**关联文档**：`documents/bug/BUG20260814163941-SFTP交互链路断裂.md`、`documents/bug/BUG20260813225039-审计缺失源系统会话标识.md`（同迭代可合并处理）

---

## 1. 背景与症状

用户在 CC 中使用 database skill 执行 DDL 反馈"失效"，DML 正常。实证定位后确认这是**多层缺陷叠加**，而非执行器单点故障：

- 所有 DDL 风险分级 ≥ HIGH（CREATE/ALTER/RENAME → HIGH；DROP/TRUNCATE → CRITICAL），**全部触发 confirm_token 二次确认**；DML 为 MEDIUM、SELECT 为 LOW，直通执行 —— 症状"DML 可用、DDL 失效"的直接来源
- confirm 确认回路机制本身完好（generate→validate→consume 实测通过），但**响应无重试指引**，agent 把 `success=False` 当终态直接放弃
- 即使过了确认，**execute_sql_text 多语句在驱动层必挂**（整段一次 `cur.execute()`，Oracle 报 ORA-00911，MySQL 拒绝 multi-statement）
- SQL*Plus 风格 `/` 分隔符被 sqlparse 切成独立碎片 `'/'` 当 SQL 执行 → 驱动报错

## 2. 实证记录（2026-08-17 本地，纯内存验证）

### 2.1 风险分级

| 语句 | 分级 | needs_confirm |
|---|---|---|
| CREATE / ALTER / RENAME | HIGH | ✅ |
| DROP / TRUNCATE | CRITICAL | ✅ |
| INSERT / UPDATE / DELETE | MEDIUM | ❒ |
| SELECT | LOW | ❒ |

confirm_token 回路 generate→validate→consume 全部正常，validate 后 consume 立即失效（一次性正确）。

### 2.2 sqlparse 分句行为

| 输入形态 | 分句结果 |
|---|---|
| 两条 DDL + `/` | 3 片：2 条语句 + 独立 `'/'` 碎片 |
| 存储过程（body 含 `;`）+ `/` | 2 片：**完整过程体（BEGIN...END 识别有效，不切碎）** + `'/'` 碎片 |
| 一段文本两条 DDL | sqlparse 可分为 2 条，**但 execute_sql_text 路径不 split，整段直接传驱动** |

### 2.3 审计行为

`registry.py:142`：工具正常返回（不抛 Python 异常）一律 `log_mcp_call(ctx, "success", ...)`。
**`success=False` 的业务失败全部被记为 success**：多语句驱动错误、确认拦截、token 无效、执行超时等均无 error_code、无 error 行。

## 3. BUG 清单（5 项）

### BUG-1：execute_sql_text 不支持多语句（Critical）

`_execute_sql_text`（`platform_mcp/skills/database/__init__.py:233`）将整段文本一次传 `sql_executor.execute_query`（`executor.py:42-70` 无分句），驱动层拒绝 multi-statement。DDL 天然脚本化（建表+索引+注释），撞得最狠；多语句 DML 同样挂（用户单条 DML 用法未暴露）。

### BUG-2：高风险多语句语义缺陷（High — 安全）

现状两个方向都有问题：
- text 路径：高风险多语句过确认后仍必挂驱动（BUG-1），确认形同虚设
- file 路径：`__init__.py:269-291` 取 max_risk **一次 confirm_token 覆盖整批语句** —— 10 条 CREATE 里藏 1 条 DROP 也只确认一次，风险遮蔽；且 `confirm.py:48-57` validate **不校验 sql_hash**（generate 存了但从不比对），token 可用于同数据源的任意其他 SQL，属潜在漏洞

### BUG-3：`/` 碎片被当 SQL 执行（High）

file 路径分句（`executor.py:80`）后 `/` 成为独立碎片，逐条执行时传给驱动必报错。SQL*Plus 风格脚本（存储过程尾部 `/` 最常见）全部受影响。text 路径修复分句后同样需要过滤。

### BUG-4：confirm 响应无重试指引（High）

- `__init__.py:217` 返回 `{"success": False, "message": "风险等级 HIGH，需要二次确认", "confirm_token": ...}` —— 没有告诉 agent "请携带 confirm_token 重新调用"
- 工具 description（`__init__.py:66/84`）完全未文档化两步确认协议
- token TTL 300 秒（`confirm.py:20`）未在响应中提示，agent 中途做其他操作超时后陷入"confirm_token 无效或已过期"死循环

### BUG-5：业务层失败一律记审计 success（High — 审计正确性）

`registry.py:130-142`：`result` 为正常返回的 dict 时不检查 `success` 字段，直接 `result_status="success"`。仅 Python 异常路径（144-153）记 error。后果：多语句驱动失败、确认拦截、token 无效、SQL 文件为空、执行超时等**全部在 pmcp_mcp_call_log / pmcp_audit_log 中呈现为成功**，审计无法对账（与 BUG-审计缺失源系统会话标识.md 的审计目标直接冲突）。

## 4. 修复设计（按用户 4 条决策落位）

### 决策评估结论

| 决策 | 结论 | 备注 |
|---|---|---|
| 1. 多语句+高风险 → 明确拒绝 + 审计 | ✅ 采纳 | text/file 两路径统一；**file 路径现有"确认后整批执行"行为同步收紧为拒绝**（行为变更，见 §7） |
| 2. 单语句/低风险多语句 `/` 修复 | ✅ 采纳 | text 路径补分句 + 逐条执行；两路径统一过滤 `/` 碎片 |
| 3. confirm msg 重试指引 | ✅ 采纳 | message + description 双修复，附 TTL 提示 |
| 4. 拦截/失败计入审计 | ✅ 采纳 | registry 按 payload success 判定 error + error_code 分类 |

### 4.1 多语句高风险拒绝（修 BUG-2，落决策 1）

**统一规则：分句后语句数 > 1 且任意语句风险 ≥ HIGH → 直接拒绝执行**（不再走 confirm）：

```python
statements = _split_statements(content)          # sqlparse 分句 + 过滤 / 碎片（§4.2）
risks = [risk_engine.analyze(s, env_code) for s in statements]
if len(statements) > 1 and any(r.needs_confirm for r in risks):
    return {
        "success": False,
        "error_code": "MULTI_STMT_HIGH_RISK",
        "message": "高风险操作，不可多语句执行：检测到 HIGH/CRITICAL 语句"
                   f"（{[s.statement_type for s in 风险语句]}），请拆分为单语句逐条执行",
        "statement_count": len(statements),
        "risk_level": max_level,
    }
```

适用范围：
- `_execute_sql_text`：新增逻辑（原路径无分句直接挂驱动）
- `_execute_sql_file`：**替换现有 max_risk + confirm 整批执行逻辑**（`__init__.py:275-291`）—— 单语句文件含 HIGH/CRITICAL 仍走 confirm（见 4.3）

PROD 场景自动兼容：PROD 下 DDL 强制 CRITICAL（`risk.py:40-43`）→ PROD 多语句 DDL 必被此规则拒绝，单语句走 confirm，语义一致。

顺带封死两个安全隐患：整批确认的风险遮蔽、multi-statement 场景 sql_hash 不校验的 token 复用面。

### 4.2 低风险多语句支持 + `/` 过滤（修 BUG-1/3，落决策 2）

**分句公共逻辑**（建议放 executor.py，text/file 共用）：

```python
def split_statements(content: str) -> list[str]:
    stmts = [s.value.strip() for s in sqlparse.parse(content) if s.value.strip()]
    return [s for s in stmts if s != "/"]   # 过滤 SQL*Plus / 碎片
```

- **execute_sql_text**：分句后逐条执行（复用/抽取 `execute_file` 的循环，`executor.py:84-90`），返回结构对齐 file 路径：`{"success": all(...), "statement_count": N, "results": [...], ...}`
- **异步判定**：`_should_run_async`（`__init__.py:43-58`）text 路径补传 statements（现仅 file 路径传，`__init__.py:293`），多语句 >3 条自动转异步；异步执行体 `_run_background`（`__init__.py:332-379`）sql_text 分支同步改为逐条执行（现在把整段 sql 传 `execute_query`）
- 分句后 0 条 → 返回 `{"success": False, "error_code": "EMPTY_SQL", "message": "SQL 内容为空"}`

### 4.3 confirm 响应重试指引（修 BUG-4，落决策 3）

两处 confirm 拦截响应（`__init__.py:215-222` 文本、`__init__.py:276-287` 文件）message 统一改为：

```
风险等级 {HIGH/CRITICAL}，需二次确认：请将本响应中的 confirm_token 作为参数重新调用本工具完成执行（token 5 分钟内有效，仅可使用一次）
```

工具 description（`__init__.py:66/84`）补文档化：

> 高风险单语句（DDL、无 WHERE 的 DELETE/UPDATE、DROP/TRUNCATE 等）首次调用返回 confirm_token，需携带该 token 重新调用完成执行。**多语句中包含高风险语句将被直接拒绝**（error_code=MULTI_STMT_HIGH_RISK），请拆分为单语句逐条执行。低风险多语句（SELECT/INSERT/UPDATE/DELETE，全中低风险）支持批量执行，SQL*Plus 风格 `/` 分隔符自动忽略。

（`validate_sql` 的 description 顺带注明其返回 `needs_confirm` 字段可用于预判。）

### 4.4 审计 result_status 修正（修 BUG-5，落决策 4）

`registry.py:_handler`（121-143 行）在 result 为 dict 时增加失败判定：

```python
if isinstance(result, dict):
    ...
    result_status = "success"
    error_code = None
    if result.get("success") is False:
        result_status = "error"
        error_code = str(result.get("error_code") or _infer_error_code(result))
    await log_mcp_call(ctx, result_status, duration_ms, error_code=error_code)
```

**error_code 分类表**（各拦截/失败点显式携带）：

| 场景 | error_code | result_status |
|---|---|---|
| 多语句含高风险被拒（4.1） | `MULTI_STMT_HIGH_RISK` | error |
| 首次确认拦截（等待 token 重试） | `CONFIRM_REQUIRED` | error（SQL 未执行，如实反映） |
| token 无效/过期 | `CONFIRM_TOKEN_INVALID` | error |
| 驱动/执行失败（含 per-statement 失败） | `EXECUTION_FAILED` | error |
| SQL 内容为空 | `EMPTY_SQL` | error |
| 正常执行 | — | success |

说明：
- `CONFIRM_REQUIRED` 记为 error 的语义：该次调用 SQL 未执行；重试成功后会有独立 success 行，审计可对账"确认→执行"两跳
- 查询类工具同规则适用（如 `get_execution_status` 查无记录返回 success=False → error），属可接受的如实记录
- `log_mcp_call`（`call_log.py:26-80`）已支持 error_code 参数透传 audit，无需改动；`confirm_token` 已进 extra_data（`registry.py:137-138`），保留

### 4.5 附带加固（低成本，建议同批）

confirm validate 补 sql_hash 校验（`confirm.py:48-57`），关闭"token 换 SQL"漏洞：

```python
def validate(self, token, tool_name, datasource_code, sql_hash: str) -> ConfirmContext | None:
    ...
    if ctx.sql_hash != sql_hash:
        return None
```

调用侧（`__init__.py:223/288`）传入与 generate 时一致的 sql/combined 哈希。

## 6. 验证方案

1. **单元**：`split_statements`（`;` 多句 / `/` 过滤 / 存储过程体完整 / 空内容）；多语句含 HIGH 拒绝（text+file）；低风险多语句逐条成功；单条 HIGH 确认拦截 msg 含重试指引与 TTL；confirm 回路 + sql_hash 不匹配拒绝；registry 对 success=False 各 error_code 记 error
2. **集成（mock 驱动）**：多语句逐条 execute 调用次数与顺序；per-statement 失败即停（对齐 execute_file 现行为）
3. **端到端（DEV，mysql-app-dev / oracle-app-dev）**：
   - 多语句全 DML（2 条 INSERT）→ success，逐条生效
   - 多语句 1 条 CREATE + 1 条 DROP → MULTI_STMT_HIGH_RISK 拒绝，审计行 result_status=error + error_code
   - 单条 CREATE TABLE → 返回 confirm_token + 指引 msg → 携带 token 重试 → 建表成功，审计两跳（error:CONFIRM_REQUIRED → success）
   - `/` 结尾脚本文件（含存储过程）→ 过滤碎片后执行成功
   - token 过期（>5min）重试 → CONFIRM_TOKEN_INVALID，审计 error
4. **回归**：全量 pytest + mypy（0 错误）+ 前端 vitest/vue-tsc；按 CLAUDE.md §部署原则 #11 三段式上线（段三冒烟含本次新 error_code 断言）

### 10.2 与设计稿的差异

| 设计稿（§4） | 实际落地 | 原因 |
|---|---|---|
| `/` 过滤条件 `s != "/"` | `set(s) <= set("/; \t\r\n")` 全空白碎片口径 | sqlparse 对无 `;` 输入（如整段 `/\n/`）返回单条含内嵌换行的碎片，`!= "/"` 漏过滤（单测实证） |
| file 路径拒绝在 resolve 前 | 拒绝在 `resolve_connection_params` 之后 | file 路径沿用"先 resolve 连接参数再读文件"的既有顺序，拒绝逻辑不受影响（text 路径为先拒绝后 resolve） |
| registry error_code 分类表全量落地 | payload 显式 error_code 透传 + 缺省 10001 | 驱动层失败（ExecutionResult 无 error_code 字段）在 skill 层统一补 EXECUTION_FAILED，其余拦截点显式携带；registry 不再硬编码 10001 |
