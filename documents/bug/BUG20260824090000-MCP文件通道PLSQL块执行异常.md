# BUG：MCP 文件通道 PL/SQL 块执行异常 — 块尾分号误剥/块撕碎、仅注释语句风险误判、超时无服务端会话终止

**严重级别**：Critical（文件通道 PL/SQL 必败）+ High（超时会话泄漏拖垮共享目标库）
**发现日期**：2026-08-24（内部人员反馈，4 次复现全部同错同位置）
**发现方式**：内部用户 `execute_sql_file` 执行匿名 PL/SQL 块（DECLARE…BEGIN…END;）编译期必败 ORA-06550/PLS-00103 → 2026-08-25 本地静态分句实测 + 本机实例逐项裁决定位
**关联文档**：`documents/bug/BUG20260817123100-SQL多语句执行异常.md`（其 §11 演进即本 BUG 主问题的第一轮修复；本 BUG 为该修复的残留边界 + 两个次级问题）

## 1. 背景与症状（原始反馈汇总，脱敏口径）

内部人员在开发本机实例（`http://127.0.0.1:9000/mcp/`，数据源为 Oracle 11.2.0.4 UAT 库，样本名 ora-app-uat）执行含匿名 PL/SQL 块的 .sql 文件（约 6KB，含注释与单条块，transfer 中转上传与直连本地路径两种方式）：

- `execute_sql_file` **~0.7s 即失败**（编译期，语句从未执行）：`ORA-06550: line N, column 3: PLS-00103: Encountered the symbol "end-of-file" when expecting one of the following: ;` —— 报错行恰为 `end;` 所在行，即**块尾最后一个分号在到达 Oracle 驱动前已被剥掉**；
- 复现矩阵 4/4 全部失败、错误逐字节相同：`end;`+行首 `/` 终结符 / 纯 `end;` / `end;`+尾行 `--` 注释 / 直连本地路径纯 `end;`；
- **对照证据**：完全相同的块经 `execute_sql_text` 提交可正常编译进入执行 → 问题定位在文件通道的语句切分/规范化环节。

同场反馈的次级问题：

| # | 现象 |
|---|---|
| 1 | `execute_sql_text` 实测无 ">5000 字符自动转异步"豁免：~6KB 语句走同步通道、300s 被杀、无 execution_id（工具文档宣称 >5000 自动转异步） |
| 2 | 每次 300s 击杀后，该数据源随即进入**数十分钟 ORA-12170（TNS:Connect timeout）**状态（`select 1 from dual` 亦不可达，约 30-55 分钟后自愈；2026-08-21/24 两次同款）—— 疑似被杀会话未正常终止 |
| 3 | 文件尾部 `--` 注释行被切成独立 UNKNOWN 语句，参与风险分级（HIGH"SQL 语句类型无法识别"）并计入 statement_count |

## 2. 裁决（2026-08-25，dev 代码 a61f1fb 静态实测 + 本机实例实测）

| 反馈项 | 裁决 | 证据 |
|---|---|---|
| 主问题：块尾分号被剥 | **核心已修，残留 2 个边界**（即本 BUG BUG-A） | 纯块 / 块+`/` / 块+普通 SQL 混合：切分正确、`end;` 保留、实例执行 success（561ms）；**前导注释+块：实例实测逐字复现同款 ORA-06550/PLS-00103**；**BOM 头文件：块被内部分号撕成 2 条残句** |
| 次级1：>5000 不转异步 | **已修**（非本 BUG 范畴）：长度阈值 V1.0 基线即有，08-17 起 text 路径补传 statements | 实测 6KB 单条 SELECT → 立即返回 execution_id → 轮询 SUCCESS。注：异步≠免 300s，`query_timeout`（默认 300s）仍逐语句生效 |
| 次级2：击杀后 ORA-12170 | **未修，设计缺口**（即本 BUG BUG-C） | 代码走读：超时仅取消协程，thick 执行线程不可取消、连接关闭与执行线程并发且失败被吞、无服务端会话终止 → 被杀会话在 Oracle 端继续执行已超时重查询，共享库过载致新连接 ORA-12170，查询自然结束才自愈 |
| 次级3：注释独立 UNKNOWN/HIGH | **未修**（即本 BUG BUG-B） | 实测块+尾注释文件 → statement_count=2、CONFIRM_REQUIRED 清单含 `"-- tail comment"` UNKNOWN/HIGH |

**反馈环境注记**：反馈测试发生在开发本机实例（UAT 数据源注册于本地系统库），当时 9000 进程未运行 08-19 修复代码（代码入库 ≠ 本地进程重启）；反馈中最小复现（纯块）在当前代码已不复现，但反馈中真实 6KB 样本（含注释）因残留边界 BUG-A 在当前代码仍会失败 —— 本 BUG 修复即针对残留。

## 3. BUG 清单（3 项）

### BUG-A：前导注释 / BOM 致块判定失效（Critical）

`split_statements` 的块判定 `_BLOCK_UNIT_START_RE.match(stmt)` 要求语句**以块关键字开头**：

- sqlparse 将**前导注释并入块语句**（`-- header\ndeclare … end;` 为一条语句）→ 正则失配 → 走普通语句路径 `rstrip(";")` → **块尾 `end;` 被剥** → Oracle 报 PLS-00103（与原始反馈同款）；语句后注释粘到下一块同样触发；
- 文件读取 `read_text(encoding="utf-8")` **不剥 BOM**：`﻿` 使 `_shield_block_semicolons` 状态机不入块模式 → **块被内部分号撕成 2 条残句**（首句只剩 declare 段），比剥分号更糟。

### BUG-B：仅注释语句参与分句/分级/执行（High）

尾部 `--` 注释被 sqlparse 切成独立语句（含字母，纯符号碎片过滤拦不住）→ 风险分级 UNKNOWN/HIGH"SQL 语句类型无法识别" → 计入 statement_count、DEV/UAT 触发多语句整批 confirm 门（合法脚本被迫二次确认）；确认后该"语句"执行必报错（空语句类驱动错误）→ **整个合法 SQL 文件整体失败**。同时干扰 ">3 条转异步" 计数。

### BUG-C：超时无服务端会话终止（High）

`execute_query` 超时路径：`wait_for` 取消 `_do_execute` 协程 → 连接上下文 `__aexit__` 在**仍在执行查询的 thick 线程脚下**关闭（失败被静默吞掉 → 连接泄漏）；服务端会话**继续执行已超时语句**，共享目标库过载 → 新连接 ORA-12170 持续数十分钟（原始反馈两次实测 30-55 分钟自愈）。

## 4. 修复设计（2026-08-25 落地）

| BUG | 修复 |
|---|---|
| A | ① 新增 `_LEADING_NOISE_RE`（BOM/空白/行注释/块注释），块判定改为**剥离前导噪声后匹配**（`_is_block_statement`）；② `_shield_block_semicolons` 状态机跳过 BOM 字符（at_unit_start 不被提前消费）；③ 文件读取两处 `utf-8` → `utf-8-sig`（`executor.execute_file` + skill 层 `_execute_sql_file`），BOM 在源头剥除（分句层兜底同步保留，覆盖 sql_text 粘贴路径） |
| B | 分句末过滤**仅注释语句**（`_is_comment_only` fullmatch 前导噪声模式）—— 不参与计数/分级/执行；纯注释文件自然落 `EMPTY_SQL` |
| C | Oracle 路径改超时可中断执行 `_execute_oracle_aborting`：`asyncio.shield` 保护连接上下文不被超时取消 → 超时后 `conn.break_()`（thick OOB，线程安全）**打断在飞调用** → 回收执行线程（连接上下文正常关闭，**服务端会话随之终止**）→ 仍按超时上报并附 `source_session`（sid/serial，供审计追踪）；break 后 15s 未回收则尽力关闭连接、放弃回收（退回旧行为并留 warning）。MySQL 路径不变（TCP 断开即服务端杀查询） |
