# BUG：服务器编码与数据源编码可为空（前端/后端/数据库三层均放行空值）

**严重级别**：Medium（数据完整性缺陷 + 业务键污染）
**发现日期**：2026-08-14
**影响版本**：Platform-MCP 当前 dev（含 Server Skill 二期专项、Phase 2 Skill 上传）
**修复优先级**：建议进入下一个迭代版本

---

## 1. 背景与审计目标

`server_code` 与 `datasource_code` 是两类目标资源的**业务主键**：

- MCP 工具调用（`execute_command` 的 `server_code` 参数、`execute_sql_text` 的 `datasource_code` 参数）直接以编码定位资源
- 用户-组权限分配（`pmcp_server_group_member` / `pmcp_datasource_group_member`）以编码对应的 id 建立关联
- 审计日志（`pmcp_audit_log.extra_data`、`pmcp_mcp_call_log.datasource_code`）以编码追溯操作对象

业务键一旦允许空串入库，调用侧 `WHERE server_code = ''` 的歧义、审计行无法定位对象、权限分配错乱等问题都会出现。

用户诉求：**该字段在前端和数据库端都不应为空**。

---

## 2. BUG 现象

新增服务器 / 新增数据源时，编码留空（或全空格）可直接保存成功：

| 层 | 现象 | 位置 |
|---|---|---|
| 前端 | 表单无任何校验规则，`server_code` / `datasource_code` 留空点"保存"直接发请求 | `ServerPage.vue:233`、`DatasourcePage.vue:156` |
| 后端 | Pydantic 裸 `str` 类型，`""` 通过校验进入 handler；查重 `WHERE code = ''` 不命中；直接 INSERT | `api/servers.py:22`、`api/datasources.py:22` |
| 数据库 | 列仅有 `NOT NULL` 约束，PostgreSQL 中 `''` ≠ NULL，空串照常入库 | `alembic/versions/001_initial_tables.py:122,149` |

**实测链路**：`POST /api/v1/servers` body 中 `server_code: ""` → Pydantic 放行 → 查重放行（无 `''` 记录）→ 凭证校验通过 → `PmcpServer(server_code='')` 入库成功。数据源侧完全相同。

**连带缺陷（复核发现，同类根因）**：两个 Create 表单中的其它 NOT NULL 必填字段（`server_name` / `datasource_name` / `host` / `username`）同样三层均不拦空串。

---

## 3. 根因（文件 : 行号）

### 根因 A — 前端表单零校验规则

`platform-mcp-frontend/src/views/server/ServerPage.vue:232` 与 `datasource/DatasourcePage.vue:155`：

```html
<el-form label-width="120px">   <!-- 无 :model / :rules / ref / prop -->
  <el-form-item label="服务器编码"><el-input v-model="form.server_code" ... /></el-form-item>
```

`el-form` 未绑定 `rules`，`el-form-item` 未声明 `prop`，`handleSubmit()` 也不调用 `formRef.validate()` —— Element Plus 校验体系完全未启用。

### 根因 B — 后端 Pydantic 裸 str

`platform_mcp/api/servers.py:21-34` 与 `platform_mcp/api/datasources.py:21-35`：

```python
class ServerCreateRequest(BaseModel):
    server_code: str        # ← 无 min_length / 无 strip，"" 与 "  " 均通过
```

Pydantic v2 中 `str` 类型对空字符串合法；handler 内查重逻辑只挡"重复"不挡"空"。

### 根因 C — 数据库 NOT NULL 挡不住空串

`alembic/versions/001_initial_tables.py:122,149`：`server_code` / `datasource_code` 仅 `nullable=False` + `UniqueConstraint`。SQL 标准中空串是非 NULL 值，NOT NULL 不拦截；唯一约束反而制造"只允许一条空串"的隐蔽上限。

---

## 4. 修复设计（三层防御）

### 4.1 前端 — 启用 Element Plus 表单校验 + 本地确定性 guard

- `el-form` 绑定 `:model="form"` `:rules="rules"` `ref="formRef"`
- 编码及其它必填字段 `el-form-item` 声明 `prop`，规则 `{ required: true, whitespace: true, message: '...不能为空', trigger: 'blur' }`（`whitespace` 拦截全空格）
- `handleSubmit()` **先做本地非空 guard**（trim 判空，空则 `ElMessage.error` 并中断），再 `await formRef.value?.validate()` 作为第二道防线

**关键发现（修复过程中实测）**：Element Plus 2.8.1 的 form-item 在当前测试环境下 promise 链 rejection reason 丢失为 `undefined`，导致 form 级 `validate()` 聚合时 `{...undefined}` 吞掉校验失败、错误地 resolve `true`（field 级 callback 形式则正确返回 `false`）。因此提交拦截不能只依赖 `formRef.validate()` 的 promise 结果，必须本地 guard 兜底；`:rules` 保留用于失焦时的字段级错误提示（`onValidationFailed` 正常渲染 error div）。

### 4.2 后端 — Pydantic Field + strip 校验器

- 编码字段：`Field(min_length=1)` + `field_validator` 先 `strip()` 再判空，`""` / `"   "` 均 422 拒绝
- 同表单其它 NOT NULL 必填字段（`server_name` / `datasource_name` / `host` / `username`）同步加同款校验（同类根因一次性收口）
- Update 请求不含编码字段（编码不可改），无需处理

### 4.3 数据库 — CHECK 约束（新增 alembic revision 004）

`001_initial_tables.py` 属已发布的 V1.0 基线修订，**不可回改**，新增 revision：

```python
# alembic/versions/004_code_nonempty_check_constraints.py
op.create_check_constraint("ck_pmcp_server_server_code_nonempty", "pmcp_server", "server_code <> ''")
op.create_check_constraint("ck_pmcp_datasource_datasource_code_nonempty", "pmcp_datasource", "datasource_code <> ''")
```

同步在 ORM 模型（`server/models.py` / `datasource/models.py`）声明 `CheckConstraint`，保持 metadata 与 DDL 一致。

**存量数据**：CHECK 约束创建时若已有空串行会失败——上线前先执行排查 SQL（预期 0 行，因空串本属非法写入）：

```sql
SELECT id FROM pmcp_server WHERE server_code = '';
SELECT id FROM pmcp_datasource WHERE datasource_code = '';
```

## 6. 验证方案

- 后端：`pytest tests/integration/test_api_servers.py tests/integration/test_api_datasources.py -v`，空串 / 全空格编码均返回 422，非空正常路径不回归
- 前端：`npx vitest run`，空编码点击保存不触发 `request.post`；`npx vue-tsc -b` 0 错误
- 数据库：本地 `python -m alembic upgrade head` 后，手工 `INSERT ... server_code = ''` 应报 CHECK 违规
- 回归：全量 pytest（基线 525+）+ mypy 0 错误 + vue-tsc + vitest 全绿

## 7. 兼容性

| 维度 | 影响 |
|---|---|
| API 行为 | 仅新增拒绝：空/全空格编码从"入库成功"变为 422；合法请求无任何变化 |
| 数据库 schema | 新增 2 个 CHECK 约束（revision 004），无列变更；存量合法数据不受影响 |
| 老数据 | 若历史上已写入空串行，约束创建会失败，需先人工清洗（见 §4.3 排查 SQL） |
| 前端 | 编辑已有记录时编码字段 disabled，校验不影响编辑流 |
