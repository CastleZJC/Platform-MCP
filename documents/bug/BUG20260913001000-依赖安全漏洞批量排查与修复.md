## 三、A 类修复明细（可利用性成立）

### A1. mcp 1.9.4 → 1.30.0（核心，AI 生态近期披露）

- **PYSEC-2026-3482（CVE-2026-52869，High 7.1，fix 1.27.2）**：SSE/有状态 Streamable HTTP 传输仅凭 session id 路由请求，不校验认证主体是否为会属主 → 认证用户间会话劫持。本项目 streamable-http 模式为**有状态**（FastMCP 默认），且多用户各持 API Key 共用一个 9000 端点，**命中**。
- **PYSEC-2026-1618（fix 1.10.0）**：会话建立后客户端故意触发异常 → 服务端未捕获 ClosedResourceError（anyio TaskGroup 包装 BaseExceptionGroup）→ DoS。**命中**——这正是 `mcp_server/__init__.py:_AuthMiddleware` 中 BaseException 兜底注释所描述的现象（当时按症状缓解，本次升级到根因修复版，中间件保留作纵深防御）。
- **PYSEC-2026-1617（DNS rebinding，fix 1.23.0）**：仅影响**无鉴权** localhost FastMCP；本项目强制 API Key 自定义 Header（跨站浏览器无法伪造）→ 原本不可利用，升级顺带默认加固。
- **PYSEC-2026-3483（WS 鉴权绕过，fix 1.28.1）**：项目未启用 websocket 传输 → 不适用，升级顺带覆盖。
- **选型**：取 1.x 末版 **1.30.0**（包含全部修复；2.x 为新大版本，遵循兼容性原则不跳）。
- **兼容性观察点**：① `mcp._mcp_server.list_tools()` 私有属性重注册（`mcp_server/__init__.py:225` 三角色 list_tools 过滤）；② `streamable_http_app()` 返回的 Starlette app 结构（transfer 路由 `app.routes.extend` 挂载 + lifespan 包装）；③ 工具注册装饰器与返回结构（structuredContent 为 2025-06-18 协议起标准行为，客户端兼容）。

### A2. starlette 0.38.6 → 1.6.0（fastapi 0.115.0 → 0.141.1 联动）

- multipart 无 filename 字段无上限缓冲（PYSEC-2026-1943，fix 0.40.0）+ 大文件解析阻塞事件循环（PYSEC-2026-1941，fix 0.47.2）：**命中**——Web Skill 包上传、附件上传走 multipart。
- Host 头未校验重建 request.url（PYSEC-2026-161，fix 1.0.1）、HTTPEndpoint getattr 方法分发（PYSEC-2026-2280，fix 1.1.0）、StaticFiles Windows UNC SSRF（PYSEC-2026-2281，fix 1.1.0，main.py SPA 托管在用；生产 Linux 不受 UNC 影响，dev Windows 受益）、request.url 路径重建（PYSEC-2026-248，fix 1.3.0）、form 限制仅对 urlencoded 失效（PYSEC-2026-249，fix 1.3.1）。
- **选型**：显式新增 `starlette==1.6.0` 钉版（安全关键面不再仅靠 fastapi 传递约束），fastapi 升至 **0.141.1**（允许 starlette 1.x 的当前最新），dry-run 解析无冲突。

### A3. python-multipart 0.0.9 → 0.0.32

- 7 条：边界前后字节跳过 DoS（fix 0.0.18）、UPLOAD_DIR+UPLOAD_KEEP_FILENAME 路径穿越（fix 0.0.22，本项目未用该非默认配置）、preamble/epilogue 大段 DoS（0.0.26）、part header DoS（0.0.27）、querystring 双分隔符解析缺陷（0.0.30 × 2）、负 Content-Length（0.0.31）。**命中**——所有 FastAPI UploadFile/Form 端点解析面。0.0.x 线无 API 变化。

### A4. sqlparse 0.5.0 → 0.6.0

- 6 条：长元组列表格式化挂起（GHSA-27jp-wm6q-gp25，fix 0.5.4）、dollar-quoted 词法 ReDoS、注释型语句 DoS、分组深度/Token 限制可绕过、reindent O(n²)、Python/PHP 输出转义缺陷（均 fix 0.6.0）。**命中**——`skills/database` 风控引擎对**用户任意 SQL** 做 sqlparse 解析，攻击者即普通 MCP 用户，DoS 面真实成立。回归重点：SQL 风控 4 级 + 多语句/PLSQL 块全套测试。

### A5. py7zr 0.22.0 → 1.1.3

- 符号链接重建逃逸目标目录（任意文件写，PYSEC-2026-2974）、归档头 numstreams O(n²)（PYSEC-2026-2973）、解压不计量总量（炸弹，PYSEC-2026-2972），均 fix 1.1.3。**命中**——`skills/upload.py:_extract_package` 对用户上传 .7z 直接 `extractall`。API（`SevenZipFile(mode="r").extractall(path=)`）1.x 不变。

### A6. aiomysql 0.2.0 → 0.3.2

- PYSEC-2026-1110（fix 0.3.0）：客户端未默认校验 local_infile 设置 → 恶意 MySQL 服务端可读客户端任意文件。利用前提为目标库被控，但目标库直连凭证由平台持有、`connect()` 参数面暴露，按纵深防御修复。连接/执行 API 0.3.x 不变。

### A7. axios 1.7.4 → 1.20.0（前端运行时依赖）

- npm audit 命中 **20 条 GHSA**（SSRF 与凭据泄漏 GHSA-jr5f-v2jv-69x6、multipart CRLF 注入、toFormData 无界递归 DoS、原型污染系列等），受影响范围 1.0.0–1.17.0。前端生产 bundle 全部 API 调用经 axios 携带 session cookie，虽当前代码仅以相对路径调用同源 API（绝对 URL SSRF 场景暂不可达），但作为运行时依赖按供应链标准升级；1.x 线向后兼容，vitest 202 用例回归。

## 四、B 类不修复（注明原因）

### 1. asyncssh 2.17.0 —— 漏洞路径未使用

PYSEC-2026-3808（fix 2.23.1）为 **SCP 客户端**路径穿越。全库仅 `asyncssh.connect` + `start_sftp_client`（`skills/server/connection.py:36,55`，SFTP get/put + exec），**无任何 `asyncssh.scp()` 调用**；且利用前提是对端为恶意/被控 SSH 服务端（目标服务器为内部纳管资产）。→ 不修复。三期：下次维护窗随手升 2.x 最新。

### 2. cryptography 43.0.1 —— 受影响路径全部未使用

6 条命中均为：X.509 证书链解析（递归/名称约束/通配符 SAN）、EC 公钥解析、OpenSSL 捆绑库的 TLS/CMS 面（完整修复需 ≥49.0.0）。项目仅用 `AESGCM` 对称加解密（`common/crypto.py`，数据源凭证 / API Key 存储），**不做证书解析、不直接经 OpenSSL 做 TLS**；且受影响输入（恶意密文/证书）需攻击者已能写系统库，越权前提不成立。→ 不修复，**三期随整体架构升级统一 ≥49.0.0**。

### 3. aiosmtplib 3.0.2 —— 输入不可控 + 跨 2 大版本升级影响 notify 稳定性

PYSEC-2026-2338（收件人地址 CRLF 命令注入）：收件人为 **admin 配置的邮件组地址**（notify 模块，非用户输入）；PYSEC-2026-3805（STARTTLS 前导明文注入）：需内网 SMTP 链路 MITM 位置。修复需 3.0.2 → **5.1.2**（跨两个大版本），邮件组提醒 ×4（outbox 模式）全链路需专项回归。→ 不修复，**三期规划**（notify 专项升级）。

### 4. black 24.8.0 / pytest 8.3.2（dev 组）—— 开发期工具不进生产产物

pytest PYSEC-2026-1845 为 UNIX 本地 `/tmp/pytest-of-{user}` 目录 DoS（本地开发机场景）；black 升级至 26.x 可能触发全库 reformat 噪音（与生产无关）。→ 不修复。

### 5. vitest 2.1.9 + @vitest/mocker（前端 dev）—— 测试期才可达

GHSA-82fw-gwwq-j7x9（mocker 重定向 mock 路径穿越/任意文件读）仅本地 `npx vitest` 运行期可达，生产 bundle 无关；修复需 vitest **5.0.0 破坏性升级**（连带 @vitest/coverage-v8）。→ 不修复，**三期随前端工具链升级**。

### 6. urllib3 2.6.3 / aiohttp 3.14.1 —— 非直接依赖且无调用路径

二者均非 `pyproject.toml` 直接钉版（urllib3 为 requests 传递、aiohttp 为本机无关包 edge-tts 带入）。本项目生产出口流量仅 httpx（内网）+ asyncssh（SFTP/SSH）+ aiosmtplib（SMTP），**无 requests/urllib3/aiohttp 调用路径**（VNF-03 不联网）。→ 不修复。

### 7. llama-cpp-python 0.3.9（model 组，本地未安装）—— 恶意模型加载不可达

近期 llama.cpp 系 CVE（CVE-2026-27940 `gguf_init_from_file_impl` 缓冲区溢出、CVE-2026-21869 CVSS 9.8、CVE-2026-78147）触发条件均为**加载攻击者构造的 GGUF 文件**。平台仅加载运维放置的离线内部权重（`settings.llm_model_path`，管理员配置非用户输入），启动前经 `scripts/_init_llm_weights.py` 魔数/体积/SHA-256/probe 校验（VNF-03 不联网）→ **无攻击者可控输入，不可利用**。历史 SSTI RCE（CVE-2024-27657，fix 0.2.71）0.3.9 已含。升级需重编译 C 扩展并重制离线生产镜像，破坏兼容。→ 不修复，**三期模型栈升级专项**。

### 8. fastembed 0.3.6 / onnx / onnxruntime（model 组，本地未安装）—— 同上不可达

CVE-2026-34445（onnx<1.21.0 `setattr` 模型元数据 RCE）、CVE-2026-28500（`onnx.hub.load` 静默加载供应链攻击）、CVE-2026-14647（onnxruntime 恶意模型 OOB）触发条件均为**加载恶意 ONNX 模型**。BGE-M3 为离线内部 int8 权重，fastembed 不调用 onnx.hub → 不可利用。→ 不修复，**三期**：升级 fastembed 时确认传递依赖 onnx ≥1.21。

### 9. MCP 生态「工具投毒 / prompt 注入」研究类 —— 面向客户端，平台为服务端

2025–2026 Invariant Labs / CSA 等披露的 tool poisoning（工具描述内嵌恶意指令）针对 **MCP 客户端**消费的元数据。本平台为 MCP **服务端**，33 个工具描述来自内部注册表（双语并列，`split_bilingual` 约束）；用户贡献 Skill 的描述/README 经 14 条合规审计 + 人工审核流后才入库。→ 非本次代码缺陷，**三期治理项**：Skill 描述控制字符清洗 + 审核检查单补充注入检查点。

### 10. element-plus 2.8.1（el-link href 校验不足，moderate）—— 组件未使用

GHSA-5m5x-9j46-h678：`el-link` 组件对 `href` 属性校验不足（`javascript:` 注入类）。全站 grep `el-link` **零使用**——前端按钮统一 `.btn` 家族（CLAUDE.md 强制项），Element Plus 仅用于表单输入/弹窗/消息等非按钮控件；漏洞路径不可达。修复版 2.14.5 在 stated dependency range 外，属破坏性升级。→ 不修复。**三期**：element-plus 常规升级时随批跨越。
