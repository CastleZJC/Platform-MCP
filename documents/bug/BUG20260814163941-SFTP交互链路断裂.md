# BUG：SFTP 交互链路断裂 — 工作站↔MCP 服务器不通、env 语义错位、中转目录与清理机制缺失

**严重级别**：Critical（核心功能链路断裂 + 安全语义错误）
**发现日期**：2026-08-14
**发现环境**：PROD（192.0.2.216，platform-mcp 部署于 /opt/appuser/mcp_app/app，PLATFORM_MCP_ENV=prod）
**关联文档**：`documents/bug/BUG20260813225039-审计缺失源系统会话标识.md`（同为审计/可运维性缺陷，可同迭代处理）

---

## 1. 背景与目标场景

用户在 Claude Code（CC，运行于 Windows 工作站）中使用 platform-mcp SFTP 能力，期望的完整链路：

```
上传：Win 工作站 ──①──▶ MCP 服务器(111) ──②SFTP──▶ 目标服务器(120)
下载：Win 工作站 ◀──①── MCP 服务器(111) ◀──②SFTP── 目标服务器(120)
```

用户期望的表达方式（对用户无感）：

> "把本地 D:\pkg\x.zip 传到 120 的 /data/deploy/ 下"

CC 应自动编排：工作站文件 → MCP 服务器中转目录 → SFTP 推到 120 → **清理中转文件**。

**当前 ①（Win ↔ MCP 服务器）链路完全不通**，只有 ②（MCP 服务器 ↔ 目标服务器）可用。

---

## 2. BUG 清单（6 项）

### BUG-1：Win → MCP 服务器链路不通（Critical）

`upload_file` 的 `local_path` 语义 = **platform-mcp 进程宿主机的文件系统路径**（`skills/server/executor.py` 用宿主机白名单校验后直接读写本地路径）。MCP 协议工具参数只传 JSON 文本、不传文件流，因此：

- DEV（platform-mcp 跑在用户 Win 本机）：`local_path=D:\x.zip` 恰好可用
- PROD（platform-mcp 跑在 111 服务器）：用户传 `D:\x.zip` → 111 上不存在 → **报错，链路断裂**

生产实测（2026-08-14，192.0.2.216）：用户在 CC 中要求上传 zip，`upload_file` 报 local 地址在服务器上不存在。**这就是链路 ① 缺失的直接表现。**

### BUG-2：白名单/env 拦截语义错位（High）

**现状**：`skills/server/executor.py:174-194`（SFTP 本地路径白名单）和 `skills/database/executor.py:96-116`（SQL 文件路径白名单）的强制拦截条件是：

```python
if settings.env == "PROD" and not allowed_sql_dirs:
    拒绝："生产环境必须配置 allowed_sql_dirs，禁止任意路径执行文件传输"
```

`settings.env` 来自 **`PLATFORM_MCP_ENV` 环境变量 / `settings-{env}.yml`（项目部署环境配置）**。

**语义错误**：白名单与 db 脚本拦截的业务语义应针对 **服务器管理/数据库管理中注册的目标资源环境（`pmcp_server.env_code` / `pmcp_datasource.env_code` = PROD）**，而不是 platform-mcp 自己部署在哪个环境。

**实际误伤场景**（生产实测）：platform-mcp 部署在 PROD，用户操作一台 **DEV 服务器** 的 SFTP —— 也被部署环境的 PROD 判定强制白名单拦截。目标资源根本不是生产，却被生产策略拦截。

### BUG-3：中转目录无默认配置（High）

生产 `settings-prod.yml:24` 实测：`allowed_sql_dirs: []`（空）。PROD + 空白名单 = 拒绝一切文件传输操作（executor.py:191），SFTP 功能整体不可用。

缺失一个**专用于 SFTP 中转的目录配置**：

- 默认值：`{app_dir}/sftp_exchange`（app 路径下）
- 用户可在配置文件中修改
- 所有 SFTP 的 MCP 端上传/下载中转统一存储于此

### BUG-4：下载链路同样断裂（Critical）

与 BUG-1 对称：`download_file` 只能拉到 MCP 服务器本地，工作站拿不到文件。需打通：

```
指定服务器路径 ──SFTP──▶ MCP 服务器 sftp_exchange ──①──▶ Win 本地
```

### BUG-5：中转文件无隔离、无清理（High — 数据泄露风险）

要求：

1. SFTP 交互**完成或失败后**，必须删除 MCP 端中转目录下的对应文件，避免文件在服务器残存泄露
2. **不得误删**：多人同时操作同名文件（如用户 A 和用户 B 都下载 `111.xlsx`）必须能区分，各自清理各自的
3. 文件的"提供"与"完成/失败后的删除"必须一一对应，不能搞错对象

当前实现完全没有该机制（`_execution_store` 只存任务元数据，不管文件）。

### BUG-6：接入指南泄露服务器文件交互路径（Medium — 安全）

Web 门户「MCP 接入指南」页面（前端 `platform-mcp-frontend/src/views/guide/McpGuidePage.vue:159` 附近，原型 `documents/ui/Platform-MCP-portal.html:1358/1367/1374/1379`）包含文案：

```
本地（settings.allowed_sql_dirs）：[]
⚠ 当前 allowed_sql_dirs 为空 — DEV 容许任意本地路径；PROD 强制要求配置，未配置时文件操作将被拒绝
```

该文案向所有门户用户暴露 MCP 服务器的文件交互路径体系，**需从 MCP 接入指南中整段删除**。

## 4. 修复设计

### 4.1 打通 Win ↔ MCP 服务器链路（修 BUG-1/4）

三个候选方案，**推荐方案 C**：

#### 方案 A：MCP 工具 + base64 分块（纯协议内）

新增工具：`stage_file_chunk(filename, content_base64, transfer_id, seq, is_last)`，CC 读本地文件分块编码调用，写入 `sftp_exchange/<transfer_id>/`。

- 优点：纯 MCP 协议内，无新攻击面
- 缺点：base64 膨胀 33%，大文件慢且耗 token，只适合 ≤10MB 小文件

#### 方案 B：Web 门户文件中转页

浏览器 multipart 上传到 FastAPI 新端点 `/api/v1/transfer/upload`（session 认证）。

- 优点：成熟、大文件友好
- 缺点：**对用户不无感**（需切换浏览器手工操作，违背需求 1 的"我只要说一句话"）

#### 方案 C（推荐）：MCP 服务器增开文件传输 HTTP 端点 + CC 本地 curl 编排

在 MCP server（:9000）的 ASGI 应用上新增（复用现有 `_AuthMiddleware` 的 PLATFORM_MCP_API_KEY Header 认证，无新端口）：

```
POST /transfer/upload              # raw body 或 multipart，Header 带 API Key
  → 写入 sftp_exchange/<transfer_id>/<filename>，返回 transfer_id
GET  /transfer/download/<transfer_id>/<filename>
  # Header 带 API Key，流式返回，CC 用 curl -o 保存到工作站
DELETE /transfer/<transfer_id>
  # 显式清理（下载场景 CC 取回后调用）
```

CC 端编排（用户无感的实现基础——CC 在工作站有 shell 能力，Win 10+ 自带 curl）：

```
上传：curl -H "PLATFORM_MCP_API_KEY: ..." --data-binary @D:\pkg\x.zip
        http://111:9000/transfer/upload?filename=x.zip   → transfer_id
      upload_file(local=/app/sftp_exchange/<tid>/x.zip,
                  server_code=120, remote=/data/deploy/)  → 成功
      [自动清理 <tid>]

下载：download_file(server_code=120, remote=/data/x.zip,
                    local=/app/sftp_exchange/<新tid>/x.zip) → 成功
      curl -H "PLATFORM_MCP_API_KEY: ..." -o D:\data\x.zip
        http://111:9000/transfer/download/<tid>/x.zip
      [CC 调 DELETE /transfer/<tid> 清理]
```

- 优点：原始二进制（无 base64 膨胀）、单端口复用、用户完全无感、大文件友好（上限对齐 SFTP 500MB）
- 缺点：HTTP 端点新增少量攻击面（API Key + 写入范围强制限定在 exchange 目录内可接受）
- 实现要点：
  - 上传写入路径必须经白名单校验：仅允许 `sftp_exchange_dir` 下、`transfer_id` 合法（uuid v4 正则）、文件名拒绝 `..`/绝对路径/空字节
  - 大小限制 500MB，超限拒绝
  - 认证失败 401，与 /mcp/ 行为一致

### 4.2 env 语义修正（修 BUG-2）

拦截条件从「部署环境」改为「**目标资源环境**」：

```python
# skills/server/executor.py — 修正前
if settings.env == "PROD" and not allowed:
    拒绝

# 修正后：取目标服务器的注册环境
server = await server_manager.get_server(server_code)
if server.env_code == "PROD" and not allowed:
    拒绝
```

`skills/database/executor.py:96-116` 同理：按 `datasource_code` 查 `pmcp_datasource.env_code`。

语义对照表：

| 概念 | 来源 | 用途 |
|---|---|---|
| 部署环境 | `PLATFORM_MCP_ENV` / `settings-{env}.yml` | 决定加载哪份配置（端口、日志级别、exchange 路径） |
| 目标资源环境 | `pmcp_server.env_code` / `pmcp_datasource.env_code` | 决定风控强度（PROD 目标 → CRITICAL/强制白名单）、权限（developer 禁 PROD） |

现有 `skills/common/permission.py` 的环境权限检查已经是按目标资源 env 做的，白名单拦截应与其对齐。

### 4.3 sftp_exchange 中转目录配置（修 BUG-3）

`platform_mcp/config.py` Settings 新增：

```python
class ServerSettings:
    sftp_exchange_dir: str = ""   # 空 = 运行时解析为 {app_dir}/sftp_exchange
```

- 默认：`{app_dir}/sftp_exchange`（app 路径下，随部署自动生效，用户可在 `settings-{env}.yml` 覆盖）
- 启动时自动创建，权限 `0700`（属主 = 运行用户，如 appuser）
- 所有 SFTP 的 MCP 端上传/下载中转**统一**存储于此
- 该目录同时是 4.1 方案 C HTTP 端点唯一的读写范围

### 4.4 隔离与清理机制（修 BUG-5）

**隔离（非显性标识）**：每次传输任务分配独立 `transfer_id`（uuid4），中转文件路径固定为：

```
{sftp_exchange_dir}/{transfer_id}/{原文件名}
```

- 用户 A 和用户 B 都下载 `111.xlsx` → 各自 `transfer_id` 目录，物理隔离，绝不混淆
- `transfer_id` 记入审计日志 `extra_data`（谁、何时、哪个文件、何时清理，全程可追溯）

**清理（完成/失败即删 + TTL 兜底）**：

| 场景 | 清理时机 | 机制 |
|---|---|---|
| 上传：exchange → 目标服务器 | `upload_file` 返回前（无论成功/失败） | 自动删除 `{exchange}/{transfer_id}/` 整个任务目录 |
| 下载：目标服务器 → exchange | CC 确认取回工作站后 | CC 显式调 `DELETE /transfer/{transfer_id}` |
| 下载：CC 未确认（会话中断/遗忘） | TTL 30 分钟 | 后台清理线程（复用 `_execution_store` TTL 模式），过期目录整删 |

**防误删铁律**（实现必须遵守）：

1. 删除目标必须严格匹配 `{exchange_dir}/{uuid4}/{filename}` 三段结构
2. `transfer_id` 必须通过 uuid v4 正则校验（`[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}`），拒绝路径穿越
3. 删除实现用 Python `pathlib` + `shutil.rmtree`，**禁止拼接 shell `rm` 命令**
4. 删除前 `resolve()` 校验最终路径仍在 `exchange_dir` 之下
5. 永不触碰 exchange 根目录本身及其他 `transfer_id` 目录

### 4.5 前端文案删除（修 BUG-6）

删除以下位置的 allowed_sql_dirs 相关文案（含"本地（settings.allowed_sql_dirs）"行、"⚠ 当前 allowed_sql_dirs 为空…"整段警告）：

- `platform-mcp-frontend/src/views/guide/McpGuidePage.vue:159` 附近
- 原型同步：`documents/ui/Platform-MCP-portal.html:1358/1367/1374/1379`（保持前端与原型对齐原则）

删除后接入指南中 SFTP 说明改为面向用户的语义（不暴露服务器内部路径机制）：

> 上传：告诉 Claude "把本地某文件传到某服务器的某路径" 即可
> 下载：告诉 Claude "把某服务器的某文件下载到本地某路径" 即可
