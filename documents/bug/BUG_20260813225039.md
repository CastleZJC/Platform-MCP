# BUG：审计日志与执行状态查询缺失源系统会话/进程标识（SID/PID）

**严重级别**：High（审计完整性 + 可运维性缺陷）
**发现日期**：2026-08-13
**影响版本**：Platform-MCP 当前 master（含 Server Skill 二期专项）
**修复优先级**：建议进入下一个迭代版本

---

## 1. 背景与审计目标

审计模块的两个根本目的：

1. **明确每个用户执行的内容**——谁、在何时、对哪个环境、执行了什么 SQL/命令、结果如何
2. **基于源系统可验证、可介入**——例如某条异步 SQL 卡死、某条远端 shell 失控时，能拿到数据库端的 SID、远端 Linux 的 PID，让 DBA / ops 在源系统侧远程 kill

第二项目的当前完全做不到。

---

## 2. BUG 现象（两层）

### 现象 A：`request_summary` 字段对 4 个工具只有 `tool=<name>`，丢掉关键入参

`platform_mcp/mcp_server/context.py:52-81` 的 `_build_request_summary()` 只识别 4 类入参：`sql_text` / `file_path` / `server_code+local_path+remote_path` / `command`。其余工具的入参 fall-through 到末尾 fallback `return f"tool={tool_name}"`。

实际影响：

| 工具 | 入参 schema | 当前 request_summary | 丢失信息 |
|---|---|---|---|
| `get_execution_status` | `{execution_id: string}`（required） | `tool=get_execution_status` | execution_id（Platform-MCP 内部 UUID） |
| `get_server_execution_status` | `{execution_id: string}`（required） | `tool=get_server_execution_status` | execution_id |
| `list_datasources` | `{env_code: string}` | `tool=list_datasources` | env_code（虽在 target_env 字段有，summary 内没有） |
| `list_servers` | `{env_code: string}` | `tool=list_servers` | env_code（同上） |

`pmcp_mcp_call_log.input_summary` 同样受影响（拼接为 `skill=database | tool=get_execution_status`）。

### 现象 B：源系统 SID/PID 完全未捕获

任何工具都没有捕获 / 暴露 / 持久化源系统会话标识：

| 源系统 | 应捕获 | 实际捕获 |
|---|---|---|
| Oracle 11g | SID + SERIAL#（DBA 用 `ALTER SYSTEM KILL SESSION 'sid,serial#'`） | 无 |
| MySQL 5.6 | CONNECTION_ID（DBA 用 `KILL <conn_id>`） | 无 |
| Linux SSH | 远端 shell PID（ops 用 `kill -9 <pid>`） | 无 |

`McpContext.extra_data` 字段（`context.py:22`）从未在 `build_context()` 中被赋值，所以源系统标识在审计侧也无任何兜底存储位置。

---

## 3. 当前状态判断逻辑（无 SID 时如何"猜"状态）

`_execution_store[execution_id]` 是 Platform-MCP 进程内 dict，状态机：

```
PENDING ──► RUNNING ──► SUCCESS
                    │
                    └──► FAILED
```

它知道的是 **"我自己的 asyncio 任务"** 的状态，不是源系统的真实状态。可信度边界：

| 场景 | 现有判断 | 可信度 |
|---|---|---|
| asyncio task 正常返回 | SUCCESS | 高 |
| asyncio task 抛异常 | FAILED | 高 |
| 任务还在跑 | RUNNING | 低（只知"我的 task 没完"，DB 端可能在 commit / rollback 任意阶段） |
| MCP 进程重启 | `_execution_store` 全丢 | 失忆（DB 会话可能还活着，但已无把柄可追） |
| SSH channel 断但远端 nohup 还在 | FAILED（channel error） | 误判（远端进程仍在跑） |
| DBA 外部 kill 了 DB 会话 | FAILED（驱动报错） | 巧合正确 |
| 长时间无响应 | 永远 RUNNING | 无法区分"真在跑" vs "挂死" |

后 4 行就是审计无法对账、运维无法介入的根源。

## 4. 根因（文件 : 行号）

### 根因 A — `_build_request_summary` 分支不全

**位置**：`platform_mcp/mcp_server/context.py:52-81`

```python
def _build_request_summary(tool_name: str, kwargs: dict) -> str:
    sql_text = kwargs.get("sql_text")
    if sql_text:
        return f"tool={tool_name} sql={str(sql_text)[:500]}"
    file_path = kwargs.get("file_path")
    if file_path:
        ...
    server_code = kwargs.get("server_code")
    local_path = kwargs.get("local_path")
    remote_path = kwargs.get("remote_path")
    if tool_name in ("upload_file", "download_file") and local_path and remote_path:
        ...
    command = kwargs.get("command")
    if command:
        ...
    return f"tool={tool_name}"   # ← 4 个工具命中此 fallback
```

缺 `execution_id` / `env_code` 分支。

### 根因 B — executor 层未采集源系统标识

- `platform_mcp/skills/database/executor.py`：Oracle / MySQL execute 路径从未读取 session 标识
- `platform_mcp/skills/server/__init__.py:_execute_command`：SSH channel 建立后从未 `echo $$` 抓 PID
- `platform_mcp/mcp_server/context.py:22`：`McpContext.extra_data` 字段从未被赋值
- `_execution_store[execution_id]`（`database/__init__.py:27`、`server/__init__.py:44`）：record dict 内无 source_session 字段

### 根因 C — 暴露层未透出

- `_get_execution_status`（`skills/database/__init__.py:404`）和 `_get_server_execution_status`（`skills/server/__init__.py:450`）返回结构里无 `source_session` 块
- `log_mcp_call`（`mcp_server/call_log.py:42, 71`）：写 audit_log / mcp_call_log 时未带 source_session，extra_data 永久为 None

## 5. 修复设计

### 5.1 核心约束：capture 零特权

| 源系统 | 标识 | 捕获 API（非特权） | 是否需要 DBA / root |
|---|---|---|---|
| Oracle 11g | SID + SERIAL# | `oracledb.Connection.session_id` / `.serial_num` 属性（OCI 客户端层维护，不发 SQL、不查 V$SESSION） | 否 |
| MySQL 5.6 | CONNECTION_ID | `SELECT CONNECTION_ID()` 任何用户可执行；或 `aiomysql.Connection.server_thread_id()` 客户端属性 | 否 |
| Linux SSH | shell PID | `echo $$` 解析远端 stdout 第一行（这个 shell 就是我们 SSH 起的，归当前 SSH 用户所有） | 否 |

**关键认知**：放弃 `SELECT SID,SERIAL# FROM V$SESSION` 路径（需要 SELECT_CATALOG_ROLE / DBA），改用 oracledb 客户端属性，零特权。`V$SESSION` / `V$MYSTAT` 全程不碰。

DBA / root 只在 **kill 动作本身**出现，由 DBA / ops 在他们自己的会话里执行：
- Oracle：`ALTER SYSTEM KILL SESSION 'sid,serial#'`（DBA 权限）
- MySQL：`KILL <conn_id>`（DBA / PROCESS 权限）
- Linux：`kill -9 <pid>`（同 UID 即可；sudo 起的子进程才需 root）

Platform-MCP 不参与 kill，框架不需要持有任何 kill 权。

### 5.2 三层修复

#### 层 1：捕获（executor 层）

**Oracle**（`skills/database/executor.py` 内，拿到 connection 之后、execute 之前）：

```python
# oracledb thick mode，connection 是 oracledb.AsyncConnection 的同步包装
# 客户端属性，不发 SQL，零特权
sid = connection.session_id
serial = connection.serial_num
source_session = {"type": "oracle", "sid": sid, "serial": serial}
```

注：因 thick mode 通过 `asyncio.run_in_executor` 包装同步调用，需在同步上下文里读这俩属性再回传。

**MySQL**（`skills/database/executor.py` 内，连接建立后）：

```python
async with conn.cursor() as cur:
    await cur.execute("SELECT CONNECTION_ID()")
    conn_id = (await cur.fetchone())[0]
source_session = {"type": "mysql", "conn_id": conn_id}
```

或更轻量：`conn.server_thread_id()`（aiomysql 客户端属性，不发 SQL）。

**Linux SSH**（`skills/server/__init__.py:_execute_command` 内，channel 建立后）：

```python
# 同步执行场景：用 sh -c 'echo $$; exec <cmd>' 包装
wrapped = f"echo $$; exec {command}"
# 读 stdout 第一行解析为 pid，后续输出是命令的真实 stdout
```

异步后台场景（`nohup` 形态）：

```python
wrapped = f"nohup {command} > /tmp/platform_mcp_{execution_id}.log 2>&1 & echo $!"
# echo $! 返回后台进程 PID
```

#### 层 2：存储

`_execution_store[execution_id]` 新增字段：

```python
record = {
```

**`_build_request_summary` 补全分支**：

## 7. 待确认 / 设计决策点

### 7.1 同步短任务是否也记 sid

- 短 SQL 同步返回时 DB session 已断，sid 记下来只能事后追责（"昨天 14:30 那条 select 的 session_id 是 X"），不能即时 kill
- **建议**：全记（sync / async 都记），代价仅是审计行多塞几个字段；事后追责场景同样有价值

### 7.2 SFTP（upload_file / download_file）记什么

SFTP 是 SSH 子系统 channel，没有传统 shell PID 概念。候选：

- **方案 A**：记 SSH session 远端进程 + 原文件路径（足够定位）
- **方案 B**：只记 SSH session 标识（channel id）
- **方案 C**：SFTP 走专属路径不记 pid（kill 场景下 SFTP 通常占带宽不占 CPU，紧急度低）

建议方案 A。

### 7.3 Oracle `connection.session_id` 在 thick mode 的可用性验证

`oracledb` 2.4.1 的 Connection 对象在 thick mode 下应提供 `session_id` / `serial_num` 属性。需在集成测试中实际连一个 Oracle 11g 实例验证（mock 测不能验证 OCI 层属性读取）。

如属性不可用，备选方案：
- 业务账号能否查 `V$MYSTAT`（部分环境 SELECT_CATALOG_ROLE 已授予普通用户）
- 业务账号能否查 `SYS_CONTEXT('USERENV','SESSIONID')`（返回 AUDSID，需 DBA 用 AUDSID 反查 SID）
